# Safe workflow speed / 安全なワークフロー高速化

## REQ-SAFE-WORKFLOW-SPEED-001: Minimize output and parallelize independent checks
Priority: must
Type: non-functional
Pattern: ubiquitous
Statement: The shipped SDD Skills shall minimize validation output and execute an explicit safe set of independent read-only checks concurrently without weakening required evidence or lifecycle ordering.
Acceptance: The `sdd-change`, `sdd-requirements`, `sdd-design`, `sdd-implementation`, `sdd-traceability`, and `sdd-quality` Skills shall use the human-readable form, without `--json`, for `requirements validate`, `constitution validate`, `design validate`, `trace build`, `trace check`, `config lint`, `mutation validate`, `model-correspondence validate`, `approval validate`, and `gate` when only the exit code and summary are consumed; these commands provide a non-zero failure exit and concise diagnostics or write authoritative evidence that can be inspected without rerunning the command. `gate --json` remains required when individual check fields are copied into evidence or used for a readiness or waiver decision. The Skills shall retain structured JSON on the first and only invocation of `approval prepare`, `workflow-verify`, HoH `run`, `resume`, and `status --run`, and any command whose result fields are needed for a hash, run ID, state, iteration, journal length, readiness decision, or waiver decision; HoH lifecycle commands shall use their bounded summary-JSON form when available. A mutating or append-only command shall not be rerun merely to obtain JSON diagnostics; its written evidence or original structured result shall be inspected instead. Summary-less `trace impact`, `graph impact`, `graph cycles`, `knowledge query`, and formal result commands shall be narrowly scoped and shall not be invoked in a default completion path unless their result is required.

After the relevant producer commands have completed, the Skills may place only independent read-only validators in one parallel tool-call batch: `requirements validate` with `constitution validate`; multiple `design validate` invocations for distinct design files; and any subset of `trace check`, `config lint`, `mutation validate`, `model-correspondence validate`, and `approval validate` whose input artifacts are already current. `trace build`, `graph index`, `knowledge build`, `gate`, `evidence refresh`, `workflow-record`, `workflow-verify`, workflow waivers, approval preparation and recording, TDD commands, change-record commands, HoH lifecycle commands, `status`, and project build/test commands shall remain sequential unless a future requirement explicitly proves disjoint writes and dependencies. Append-only writes, including `workflow-record`, change-record commands, approval recording, TDD evidence recording, and HoH journal appends, shall remain sequential. Requirements approval shall precede design, design approval shall precede Red, Red shall precede implementation, implementation shall precede Green, `trace build` shall precede `trace check` and `trace impact`, and `graph index` shall precede graph consumers. Deterministic distribution tests shall assert the required and forbidden command forms and the explicit parallel/sequential sets without measuring wall-clock time.

## REQ-SAFE-WORKFLOW-SPEED-002: Document the safe batching boundary
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The English and Japanese release entry points shall disclose the complete safe batching boundary in their own language.
Acceptance: Under the Workflow section of `README.md` and the ワークフロー section of `README-ja.md`, each README shall contain one contiguous passage in its own language naming the complete parallel allowlist: `requirements validate` with `constitution validate`; multiple `design validate` invocations for distinct files; and any independent subset of `trace check`, `config lint`, `mutation validate`, `model-correspondence validate`, and `approval validate` after their producer artifacts are current. The same passage shall state that all other commands remain sequential, including artifact producers (`trace build`, `graph index`, `knowledge build`, and `evidence refresh`), consumers outside the allowlist or with stale inputs, gates, `workflow-verify`, `workflow-record`, workflow waivers, approval preparation and recording, TDD commands, change-record commands, HoH lifecycle commands, `status`, project build/test commands, and append-only writes (`workflow-record`, change-record commands, approval recording, TDD evidence recording, and HoH journal appends). The same passage shall also state the required order: requirements approval before design, design approval before Red, Red before implementation, implementation before Green, `trace build` before trace consumers, and `graph index` before graph consumers. Deterministic release-document tests shall normalize whitespace and assert the named parallel allowlist and the sequential/order boundary using each document's own-language wording, including Japanese source strings for `README-ja.md`.

## REQ-SAFE-WORKFLOW-SPEED-003: Reuse an exact fresh code graph
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While a code-graph construction request uses the default read-write or cache-read-only policy and an identity-bound persisted code graph exactly matches all current graph inputs, the system shall reuse that graph instead of reconstructing the compiler-backed graph.
Acceptance: The complete cache-policy set shall be read-write, cache-read-only, forced rebuild-and-write, and fully isolated bypass; read-write is the default. `graph index` without `--changed`, `graph gate`, the code-graph portion of `gate`, and change-impact fingerprint collection shall use one shared freshness decision and return graph content equivalent to a complete rebuild. Cache identity shall use a new persisted schema version and bind the installed musubix4 package version, an explicit graph-extractor algorithm version, a SHA-256 digest over the complete first-party transitive module closure reachable from the executing graph-extractor module, the executing TypeScript version, and the complete graph-input fingerprint map; the closure digest shall hash module paths normalized relative to the musubix4 package root and raw module bytes in sorted path order so a change to any first-party extractor helper invalidates the cache without making identity depend on the installation directory. Graph inputs shall include supported source files, graph-relevant manifests and compiler configuration, and dependency lockfiles that govern module/type resolution. A deterministic performance test shall warm the cache with one complete public indexing invocation, create a separate per-invocation operation recorder for every counted invocation, invoke the same API again without changing any graph input, and emit a passing `TEST-SAFE-WORKFLOW-SPEED-004` result whose post-warm-up `typescriptProgramBuilds` operation count is explicitly 0 rather than omitted; the baseline from the release immediately preceding CHANGE-0018, v0.1.2, is 1 for the same invocation. A forced rebuild-and-write mode shall ignore every readable cache, perform exactly 1 complete construction, and atomically replace the persisted cache; the test shall seed a distinguishable structurally valid fresh cache, invoke that mode with its own recorder, assert exactly 1 construction, prove the persisted bytes were replaced with the rebuilt graph, and prove a following `loadGraph` returns that rebuilt graph. The same test shall seed a distinguishable structurally valid fresh cache, invoke the internal API-only fully isolated bypass mode with its own recorder, assert exactly 1 construction, prove the returned graph is the rebuilt graph rather than the seeded graph, and prove the seeded cache bytes remain byte-identical; a separate absent-cache bypass case shall prove no cache file is created. The `test` command entry in `.musubix/config.json` shall remain byte-identical to its `.musubix/policy-baseline.json` definition. The existing `scripts/run-full-tests.mjs` report-producing runner shall be the only command report that emits `operations.typescriptProgramBuilds` for `TEST-SAFE-WORKFLOW-SPEED-004`; before starting Vitest it shall create a fresh unpredictable run nonce and pass the nonce plus an internal `.test-work` sidecar path through environment variables without changing the configured command definition. The executed TEST-SAFE-WORKFLOW-SPEED-004 test shall write the actual post-warm-up count and matching nonce to that sidecar. After Vitest succeeds, the runner shall accept only a readable structurally valid sidecar carrying the current nonce, augment the one existing Vitest-produced TEST-SAFE-WORKFLOW-SPEED-004 entry rather than appending a synthetic or duplicate entry, emit exactly one entry with the measured operation value and existing authoritative `testFiles` binding in `musubix-json`, and delete the sidecar; an absent, unreadable, malformed, stale-nonce, duplicate-test, or non-executed-test sidecar shall omit `operations` and produce an actionable failure naming the sidecar and regeneration command. TDD and any other report entry for that test ID shall omit `operations`. Missing, malformed, schema-incompatible, producer-incompatible, or stale cache content, any added or removed graph input, and any changed input bytes shall perform exactly 1 complete TypeScript Program construction for TypeScript/JavaScript inputs and persist an atomically replaced graph under read-write policy. `graph index --changed` shall select forced rebuild-and-write mode so subsequent persisted-graph consumers succeed. Existing `loadGraph`-based persisted-graph consumers, including `graph impact` and `graph cycles`, shall reject missing, malformed, schema-incompatible, producer-incompatible, or stale caches with an actionable rebuild instruction rather than rebuilding implicitly. Cache-read-only change-impact collection may reuse a fresh persisted graph but shall not write it; fully isolated bypass shall neither read nor write persisted cache bytes. Persistence failure shall remain an explicit command failure and shall not return a success-shaped result. `generatedAt` shall denote the time the graph content was constructed rather than the time a command returned it, so reuse shall intentionally preserve the cached value; this timestamp meaning is the sole intended observable difference from v0.1.2 command-invocation timestamps. Reuse shall not change the returned files, unsupported files, imports, entrypoints, symbols, calls, diagnostics, fingerprints, or producer identity, and shall not rewrite unchanged cache bytes.
