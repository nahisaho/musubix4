# Automatic Harness on Harness coding / Harness on Harness コーディング自動起動

## REQ-AUTOMATIC-HOH-CODING-001: Route top-level coding requests through HoH
Priority: must
Type: functional
Pattern: event-driven
Statement: When GitHub Copilot CLI receives a top-level natural-language request that requires changing repository files which affect executable behavior and the repository has HoH configuration, the system shall route the request through one MUSUBIX4 Harness-of-Harness run before directly editing those files.
Acceptance: A top-level request is a new request processed with repository custom instructions while trimmed `MUSUBIX4_HOH_RUN_ID` is empty. Executable-behavior changes include source, test, build-script, and runtime-configuration creation or modification requested with development intent such as develop, build, create, implement, add, change, or fix. Documentation-only, investigation, review, explanation, a request that explicitly names an existing `CHANGE-*` ID for continuation, and a repository with neither `.musubix/hoh.json` nor `.musubix/config.json#/hoh` shall retain the direct SDD Skill workflow. For a qualifying configured request, the shipped `sdd-change` Skill shall invoke `npx musubix4 run --prompt <request> --summary-json` exactly once using the complete user request without truncation as the public specification, and then invoke `npx musubix4 resume <run-id> --summary-json` one transition at a time. Summary JSON shall contain only the run ID, state, iteration, journal length, evidence counters, evidence-claim statuses, deployment-command presence, terminal reason, and required operator action. Before each resume, the Skill shall evaluate the preceding summary. It shall continue through `created`, `planned`, `candidate`, and `qa`; stop successfully at `deployed`; or, without issuing another resume, stop successfully at `ready` when deploy, verify, and rollback commands are not all configured, `evidenceClaims` is non-empty, every entry is `verified`, and `evidence.unresolved` and `evidence.regressions` are 0. A `ready` state that does not meet those conditions and every `approval-paused`, `amendment-required`, `recovered`, `rollback-failed`, `stopped`, or `failed` state shall be reported with its required operator action as a blocker. The Skill shall also report a blocker after 128 resume attempts or whenever a resume returns the same state, iteration, and journal length. Once routed, the top-level Skill shall not perform a second direct requirements/design/TDD/implementation lifecycle outside HoH; the HoH Planner, Developer, QA, Reviewer, verified automatic approval, and durable evidence lifecycle own that request. An oversized or rejected specification, a non-zero command exit, malformed summary JSON, a missing run ID, a no-progress result, or an action-required/unsuccessful terminal state shall produce an explicit user-visible blocker and zero direct implementation-file edits; direct implementation fallback after routing is forbidden. Every local HoH role invocation shall receive `MUSUBIX4_HOH_RUN_ID` as a single-key override set to the current non-empty run ID while preserving the subprocess's existing environment and secret-redaction inputs. When `musubix4 run`, `musubix4 resume`, or `musubix4 protected-set amend` observes a non-empty trimmed `MUSUBIX4_HOH_RUN_ID`, it shall perform no run mutation or role invocation, emit structured JSON containing the exact message `Nested Harness-of-Harness orchestration is forbidden while MUSUBIX4_HOH_RUN_ID is set.` when a JSON output option is used, emit the same message in human-readable mode, and exit with code 2. Focused tests shall verify the routing text, compact projection, environment propagation, and guarded CLI behavior.
