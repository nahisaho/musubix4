# ADR-0009: Verified-only automatic approval boundaries

## Context / 背景

Interactive requirements, design, amendment, and release approvals prevent the
Harness-of-Harness from completing application development autonomously. An
unconditional self-approval mechanism would let artifact producers weaken
quality policy, omit reviewed files, reuse stale evidence, or deploy without an
independent decision.

## Decision / 決定

Use automatic run-bound approval only through a distinct read-only Reviewer
invocation and deterministic local validators. Key every boundary by run,
canonical stage, boundary kind, and amendment episode/attempt when applicable.
Require exact manifest/change-set coverage, fresh single-use nonces, fixed
attempt bounds, immutable run-start waivers, and zero admissible findings.
Release additionally reruns all seven mandatory gates in a fresh isolated
checkout of the accepted candidate. Inherited MUSUBIX3 approval records remain
compatible artifacts but are inert for MUSUBIX4 run advancement.

## Rejected alternatives / 却下案

- Unconditional approval at each boundary: rejected because producers could
  approve incomplete or weakened evidence.
- Reusing the producing Planner or Developer session as reviewer: rejected
  because it is self-approval and carries hidden producer state.
- One run-wide approval retry counter: rejected because initial requirements
  and separate amendment attempts would consume each other's retry budget.
- Treating legacy MUSUBIX3 approval evidence as run approval: rejected because
  it lacks the run, boundary, nonce, reviewer, and gate bindings.

## Consequences / 結果

The runtime can cross every approval boundary without user confirmation only
when deterministic evidence and an independent Reviewer agree. Reviewer calls
consume the same credit and active-time budgets as other roles. Boundary
failures are auditable and bounded; invalid static configuration or oversized
review input fails before spawning Reviewer.
