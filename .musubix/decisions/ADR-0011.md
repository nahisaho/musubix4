# ADR-0011: HoH routing and dependency-aware Skill execution

## Context / 背景

Direct Skill implementation bypasses Harness on Harness independence, while
unbounded or nested HoH startup can recurse, consume budgets, or falsely report
completion. The SDD Skills also spend avoidable time and context on large JSON
payloads and sequential execution of checks that have no dependency.

## Decision / 決定

Route only top-level executable-behavior development requests in repositories
with HoH configuration through one HoH run; unconfigured repositories retain
the direct SDD workflow. Mark autonomous Copilot role subprocesses with the
active run ID and reject nested `run`, `resume`, and protected-set amendment
commands at the CLI boundary. Treat deployment as successful only
at `deployed`; for configurations without a complete deployment command set,
accept `ready` only with a non-empty fully verified claim set and zero unresolved
or regression evidence, before issuing another resume. Use a bounded structured
run projection instead of repeatedly emitting the cumulative durable record.

For direct SDD workflows, prefer concise output and parallelize only independent
read-only checks. Preserve every approval, TDD, append-only evidence, and
producer-before-consumer boundary. Use JSON only when a field must be parsed or
a failed read-only command needs structured diagnosis; never rerun a mutating
or append-only command merely to obtain diagnostics. Disclose the complete safe
parallel allowlist, sequential boundary, and required order in both English
and Japanese release entry points so users do not infer that every read-only
command is safe to batch.

## Rejected alternatives / 却下案

- Start HoH from every coding-capable role: rejected because it permits recursive
  orchestration and unbounded budget consumption.
- Fall back to direct implementation when HoH fails: rejected because it silently
  removes the requested independence and evidence guarantees.
- Treat any `ready` run as successful: rejected because empty or unresolved claim
  sets do not prove readiness.
- Run every validation concurrently: rejected because trace, graph, approval,
  TDD, and append-only evidence commands have ordering or write conflicts.
- Always request JSON: rejected because generated graph payloads are large and
  routine success paths need only a concise status.
- Document only the optimization headline: rejected because omitting the
  sequential exceptions and ordering contract would encourage unsafe batching.

## Consequences / 結果

Qualifying top-level development requests either complete through one bounded
HoH lifecycle or stop with an explicit blocker. Nested orchestration is rejected
before persistence. Direct workflows retain their evidence semantics while
reducing successful-path output and overlapping only checks proven independent.
Both release entry points carry the same safety boundary in their own language.
