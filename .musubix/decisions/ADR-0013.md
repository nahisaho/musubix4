# ADR-0013: Normalize racy-clean baseline dirt and restore rejected candidates before retry

## Status
Accepted

## Context
CHANGE-0015 fixes two coupled HoH defects in the Git candidate store. First,
when candidate checks reject a snapshot but `blockerRepairRetryLimit` has not
been exhausted, HoH preserved the rejected candidate ref yet left the rejected
candidate's tracked changes in the real worktree and real index. The next
`resume` then observed HoH's own leftovers as external mutation and stopped
before the retry could begin. Second, initialization baseline capture trusted
Git staged/unstaged status classifications too directly: a racily-clean path
whose worktree bytes and mode already matched the copied index entry could be
persisted as `unstagedIdentity: "modified"`, poisoning every later isolation
comparison even though the content was clean.

## Decision
Persist initialization-dirty tracked paths in baseline schema version 2 with
both the existing content digest and restorable worktree bytes, staged content
bytes whenever a present copied-index entry differs from initialization `HEAD`,
while an absent copied-index entry records a staged deletion without staged
bytes, plus
Git-effective mode, existence, copied-index entry, and staged/unstaged identity.
During every isolated candidate-state read, continue reading status from a
copied private index, but clear a false unstaged identity when the path's
filter-applied Git blob identity and Git-effective mode equal the copied-index
entry. Exclude the path from the dirty set only when that copied-index entry
also equals initialization `HEAD`. Persist raw worktree bytes and raw staged
blob bytes separately; restore staged bytes with Git filters disabled and
install the resulting object directly into the index. Restore a recorded
worktree deletion by removing that tracked worktree entry after target
materialization, independently of whether its recorded index entry is present
or is a staged deletion. Conditional byte fields
are omitted rather than stored as null, and the configured total/per-path dirty
byte bound fails initialization before a baseline is written. During
recovery after any closed-set blocker-repair-consuming rejection, restore every clean-at-initialize tracked
path in the real worktree/index to the last preservation candidate or run base,
then reapply each persisted initialization-dirty tracked path's recorded index
entry and content bytes, removing the index entry for a recorded staged
deletion. Leave all untracked paths untouched. Key each durable blocker increment to a canonical digest of run ID, iteration,
the journal-persisted candidate snapshot ordinal, resolved rejected-candidate
commit OID, and one literal kind from `candidate-checks-failed`,
`qa-tree-modified`, or `declared-surface-divergence`, so interruption or resume
cannot double-count it and byte-identical later snapshots remain distinct.
The journal reuses an ordinal only for the same incomplete snapshot-check
attempt after interruption; a completed attempt closes that identity and a
later snapshot attempt always receives a fresh ordinal even when its commit OID
is identical.
Keep rejected candidate refs for diagnosis and allow a retry transition only
after a fresh isolation observation and protected-set digest both match the
expected recovered state. Persist the failure-keyed increment before recovery;
retain it while the failure count is less than or equal to the retry limit and
after any failed recovery, and reset it to zero
after either an accepted candidate or a retry-exhausted rollback has been
verified successfully and closes the blocker-repair episode.
The configured limit counts retries after the initial rejection: with limit 2,
failure counts 1 and 2 retry and count 3 rolls back. At every decisive
closed-set rejection, before the keyed increment and recovery and regardless of
whether retry or retry-exhausted rollback follows, retain the rejected snapshot
under an ordinal-suffixed immutable ref so a later snapshot in the same
iteration cannot overwrite its diagnostic evidence. The ordinal is bound to
the resolved commit OID and can be reused after interruption only for that same
incomplete OID-bound check attempt.

## Rejected alternatives
- **Refresh or rewrite the real index during initialization.** `git
  update-index --refresh` can mask the racily-clean symptom but mutates user
  state and violates the baseline-capture requirement to observe without
  rewriting the real index or worktree.
- **Persist only hashes for initialization-dirty content and reconstruct later
  from `HEAD` or the rejected candidate.** Recovery needs exact user dirt, not
  just proof that some dirt existed, and reconstruction from commits cannot
  restore staged+unstaged tracked states whose worktree bytes never existed in
  a commit.
- **Delete rejected candidate refs during rollback.** The refs are required
  diagnostic evidence for rejected-candidate analysis and remain safe once the
  real worktree/index has been restored independently.

## Consequences
- New baselines use schema version 2; unsupported older shapes fail closed
  instead of silently loading with insufficient restoration data.
- Candidate retries and REQ-018 rollbacks now recover the real worktree/index
  to the preservation target plus initialization dirt, so HoH no longer trips
  over its own rejected-candidate leftovers on the next resume.
- Racy-clean false dirt is normalized away only when worktree bytes and mode
  truly match the copied index entry; same-size or same-mtime real edits remain
  dirty and keep the existing regression coverage meaningful.
