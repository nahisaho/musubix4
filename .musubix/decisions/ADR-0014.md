# ADR-0014: Preserve superseded quality checkpoints with sequence-scoped order records

## Status
Accepted

## Context
Staged changes originally allowed only one `quality` phase record. When a defect
was discovered and corrected after that checkpoint, later Green evidence made
the original quality order invalid, but the recorder rejected a replacement as
a duplicate. Editing or deleting the original checkpoint would destroy audit
history, while leaving it current made the change permanently unable to satisfy
phase ordering.

Quality order records also need to tolerate an interrupted append in which the
order log is written but the corresponding change checkpoint is not. A retry
must not collide with that stale record, and validation must distinguish an
unmatched historical checkpoint from an unmatched order-only audit record.

## Decision
Treat `phases.quality` as the authoritative current checkpoint and retain
superseded checkpoints in an optional ordered `qualityHistory` array. Permit a
refresh only when the maximum Green order returned by `effectiveBatches(change)`
is strictly later than the current quality order and all declared requirements
have Green coverage.

Keep the first quality checkpoint backward-compatible with schema version 1:
it has neither `qualityHistory` nor `orderDetail`. On refresh, move the previous
checkpoint into history and assign the new current checkpoint
`orderDetail = quality-revision:<n>`, where `<n>` is the resulting history
length. Resolve current and historical checkpoints against order records by
change ID, phase, optional detail, and exact monotonic sequence.

Extend the existing waiver sequence-scoping rule specifically to change-quality
records without changing waiver behavior. This permits a retry to append the
same deterministic quality revision detail after an interrupted order-only
write. A checkpoint without a matching order record is blocking; an order-only
quality record remains a warning because it is immutable audit evidence that
must not prevent a later valid append.

A non-empty quality history requires a current quality checkpoint with the
matching revision detail. The recorder validates this invariant on every
quality recording before any Green or refresh guard, and the validator reports
violations as unwaivable `CHANGE_QUALITY_HISTORY_SCHEMA`. An unmatched
historical checkpoint uses `CHANGE_QUALITY_HISTORY_ORPHAN`; the existing
singular-phase `CHANGE_ORDER_MISMATCH` contract remains authoritative for an
unmatched current quality checkpoint.

## Rejected alternatives
- **Overwrite the original quality checkpoint.** This removes the evidence that
  quality was assessed before the later correction and breaks auditability.
- **Delete an interrupted order-only record before retrying.** The order log is
  append-only and hash-chained; deleting a record would invalidate subsequent
  evidence and conceal the interrupted attempt.
- **Use only the revision detail as the order key.** A retry after an
  interrupted append would collide with the existing detail and permanently
  block recovery.
- **Permit unconditional quality replacement.** Refresh without later Green
  would allow meaningless duplicate checkpoints and weaken phase-order proof.

## Consequences
- A staged change can recover from a quality-before-later-Green ordering defect
  without rewriting prior evidence when an unused requirement batch can supply
  later Green. This decision does not make Red/Implementation/Green batches
  revisable, so a single-requirement change or an already-used batch cannot
  create another Green through this mechanism; operators must open a follow-up
  change rather than edit evidence in that case.
- Superseded checkpoints remain inspectable and are validated against their
  original order records.
- Order-only quality records are visible as warnings but do not block a valid
  retry with the same revision detail.
- Sequence-scoped quality keys intentionally make order-log duplicate detection
  inapplicable to quality records; checkpoint history validation is the
  authoritative duplicate/order defense.
- Quality history is append-only and currently has no retention or compaction
  limit.
- A missing current checkpoint can also produce the existing waivable
  `CHANGE_PHASE_MISSING`, but the co-occurring unwaivable history-schema error
  remains the authoritative fail-closed result.
- Consumers that understand only schema version 1 continue to see the same
  first-quality shape; revision fields are optional additions.
