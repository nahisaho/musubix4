# ADR-0002: Copy the MUSUBIX3 baseline into one successor CLI

## Context / 背景

MUSUBIX4 must retain every MUSUBIX3 command and existing `.musubix` artifact
contract while adding a long-running runtime. A wrapper dependency would split
configuration, release, and compatibility ownership across two executables.

## Decision / 決定

Copy baseline commit `c0b20f06727bceb04eeec181d95af9047b1981de` into this
repository without its Git history, rename the package and executable to
`musubix4`, retain inherited module boundaries, and add HoH functionality as
new analysis/runtime modules and CLI registrations.

Freeze compatibility independently of the evolving candidate. A canonical
`baseline-specs/baseline.manifest.json` pins the upstream repository/commit,
regeneration procedure ID/version, upstream-only command surface, behavioral
goldens, inherited tests/fixtures, historical requirement-to-code/test mapping,
and regeneration attestation by path and SHA-256. Regeneration is a
deterministic maintainer/CI operation outside an autonomous run with separately
authorized upstream access. Runs perform local digest and attestation
verification only and compare the candidate against the verified frozen oracle.

The compatibility component, not the CLI component, generates the canonical
candidate-local declared command-surface snapshot and validates the protected
`.musubix/compatibility/command-collisions.json`. The registered HoH commands
include `musubix4 run`, `musubix4 resume <run-id>`, `musubix4 stop <run-id>`,
`musubix4 status --run <run-id>`, and `musubix4 protected-set amend <run-id>
--collision-inventory <path>`. Bare `musubix4 status` remains inherited and the
HoH form is an additive-argument resolution. One versioned extractor produces
the deterministic declared path/option set immediately after candidate commit
and the same set again in QA. Before QA provisioning, malformed, duplicate,
conflicting, missing candidate-path, and extra stale entries absent from both
upstream and candidate surfaces cause a non-destructive `amendment-required`
stop that retains the original candidate and consumes no blocker-repair or
stagnation budget. QA separately executes pinned invocations after provisioning;
a present but incorrect or unreachable resolution fails candidate acceptance
through usability and inherited-compatibility evidence rather than amendment.

The regeneration attestation is digest-pinned. It makes no signature or trust
claim unless a later ADR explicitly defines a trust anchor, key lifecycle,
verification algorithm, and failure policy.

## Rejected alternatives / 却下案

- Runtime wrapper around the published `musubix3` package: rejected because
  exact CLI compatibility and atomic configuration evolution would depend on
  two independently versioned packages.
- Separate core and runtime products: rejected for v1 because the user chose a
  single successor CLI.
- Query or rebuild the upstream oracle during each run: rejected because it
  makes compatibility depend on network access, mutable upstream state, and
  role permissions.
- Rename inherited `status`: rejected because it would break the frozen
  MUSUBIX3 invocation.

## Consequences / 結果

The source import and frozen oracle are larger. Intentional collision-inventory
changes use the requirements-approved in-run amendment cycle; baseline,
specification, or manifest-enumerated compatibility test/fixture changes require
out-of-run regeneration or update, renewed approvals, and a new run. In return,
inherited tests remain auditable compatibility evidence and MUSUBIX4 owns
security fixes and future schema evolution without consulting upstream during a
run.
