# ADR-0012: Persist candidate-isolation baselines per run

## Context / 背景

HoH `run` and `resume` execute in separate CLI processes. A candidate baseline
held only by a process-local Git adapter is lost on resume, so a new adapter can
misclassify Developer output as pre-existing user dirt and produce an empty or
mixed candidate. The real worktree and Git index must remain untouched while
staged and unstaged states are observed.

## Decision / 決定

Persist one immutable, digest-bound candidate-isolation baseline in the durable
run directory before the first Planner invocation. Its SHA-256 covers canonical
UTF-8 JSON containing the schema version, initialization `HEAD`, and sorted
dirty-path content, mode, existence, index-entry, staged, and unstaged
fingerprints in fixed field order. Create a MUSUBIX4-owned base ref before
persisting the baseline so the recorded commit remains reachable. Later CLI
processes load and verify the baseline and base ref verbatim, build candidate
indexes from the recorded commit, and never recompute the baseline from current
`HEAD`.

Use run-private Git index files for observation and every candidate-producing
operation, and verify real-index and worktree signatures before and after each
operation. Paths clean at initialization may contribute run output. Paths dirty
at initialization resolve to recorded base bytes only while all recorded
dimensions remain unchanged. Extra-path expansion filters and records tracked
matches before adding untracked paths. Protected-set verification uses the same
isolation-resolved virtual or candidate tree bytes. Any dirty-path mismatch
enters the non-repairable `candidate-isolation-required` operator stop, removes
a provisional conflicting ref, and consumes no repair or stagnation budget.
Recovery idempotently removes orphan provisional stage refs while preserving
the base and accepted evidence refs.

If a crash occurs after baseline persistence but before the initialization
transition, recovery verifies the baseline and recorded commit, idempotently
reasserts the base ref, and journals completion without rewriting baseline
bytes. Only an incomplete initialization with no baseline and no role-start
transition may delete its provisional base ref and repeat observation; absence
after any role start or an unresolvable recorded commit fails closed.

## Rejected alternatives / 却下案

- Keep the baseline in process memory: rejected because `resume` creates a new
  process and adapter.
- Recompute the baseline during resume: rejected because run output would be
  reclassified as pre-existing user changes.
- Three-way merge or patch extraction on the same dirty path: rejected because
  ownership is ambiguous and can silently absorb or discard user changes.
- Reject every run that starts dirty: rejected because independent paths can be
  isolated deterministically without modifying the user's workspace.
- Treat an isolation conflict as a normal Developer retry: rejected because the
  conflicting user state cannot be repaired safely by autonomous code changes.

## Consequences / 結果

Run directories contain one additional integrity-checked artifact. Before
initialization completes, absence permits observation to restart only when no
role has started, while a valid baseline with a resolvable recorded commit
permits base-ref reassertion; absence after a role start and any present invalid
or unavailable-base baseline fail closed. After completion, an absent,
malformed, tampered, or unavailable-base baseline fails closed. Branch movement after initialization
does not change candidate ancestry. An operator may restore offending paths to
the recorded fingerprint and resume the same iteration; any intentional
different state requires a new run and baseline.
