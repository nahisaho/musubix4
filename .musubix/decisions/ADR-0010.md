# ADR-0010: Root package version authority and streamed archive verification

## Context / 背景

The executable, npm package, private workspace manifests, lockfile, Copilot
plugin manifests, README files, CHANGELOG, and generated archive can each carry
or expose a release version. The repository inherited prerelease-development
history through `0.1.18`, but the independently named `musubix4` package has no
published npm, Git tag, or GitHub Release history and its first public release
is intentionally `0.1.0`. Source, compiled, installed, and symlinked CLI layouts
also have different fixed relative depths, and archive verification must work
across the supported Node.js and operating-system matrix.

## Decision / 決定

Treat the root `package.json` whose name is exactly `musubix4` as the sole
release-version authority. Locate it through a bounded realpath-based ancestor
search implemented in the analysis layer and shared by CLI version, workflow
event recording, and package-asset resolution without creating an
analysis-to-CLI dependency. Verify repository
metadata, documentation, and the built CLI through one release verifier.
Verify actual npm archive contents by streaming selected regular files with a
direct dev-only `tar` dependency whose engine range supports Node.js 20, 22,
and 24. Canonicalize BOM and line endings before documentation hashing and
matching. Bind the immutable pre-change CHANGELOG heading fixture by parsing
its approved SHA-256 from REQ-AUTONOMOUS-DEVELOPMENT-019 rather than trusting a
digest stored beside the mutable fixture. Release verification intentionally
accepts stable versions only; ordinary CLI identity may still expose a valid
prerelease package version.

New workflow declarations read the package authority when they are appended;
the evidence-root path and process working directory do not participate in
version resolution, and existing append-only declarations are never rewritten.
Shipped Skill sources carry no `musubix3` token. Other regular UTF-8 text files
in both the configured npm file set and generated archive are checked for stale
musubix3 command invocations while preserving non-command compatibility and
lineage references.

For the first public release, replace the prerelease-development heading fixture
with the approved single baseline `## 0.1.0 - 2026-09-16`, retain the fixture
schema and deterministic serialization, and pin its new digest in
REQ-AUTONOMOUS-DEVELOPMENT-019. Later releases may prepend newer dated stable
headings but shall retain this baseline as the contiguous trailing block.
The date is the approved baseline date for the initial history reset; it is not
derived dynamically from a later publication timestamp.

## Rejected alternatives / 却下案

- Keep a version literal in `main.ts`: rejected because it duplicates package
  metadata and caused the current drift.
- Use a fixed relative path from `import.meta.url`: rejected because source and
  compiled layouts have different depths.
- Select the nearest ancestor `package.json`: rejected because source execution
  would select the private `@musubix4/cli` workspace.
- Parse tar headers manually: rejected because extended headers, path handling,
  and platform compatibility would create unnecessary release risk.
- Inspect only `npm pack --dry-run`: rejected because it proves the file list
  but not the values stored inside the generated archive.
- Publish `musubix4` first as 0.1.18 because the implementation was forked from
  musubix3: rejected because `musubix4` is a distinct unpublished package and
  inheriting that number would imply a public release history that does not
  exist.

## Consequences / 結果

CLI startup fails through the existing structured error boundary when the named
root manifest is unavailable or invalid. Repository and archive checks share
one version contract, and the packed artifact is inspected without extraction.
CLI startup and workflow recording share the named-root resolver and retain its
structured not-found and invalid-version failures.
The project gains one direct dev-only dependency and its five-package
transitive development tree; the lockfile records the selected parser version,
while runtime consumers gain no dependency.
The public documentation and metadata start at 0.1.0, while the approved
fixture preserves that initial release as the permanent changelog anchor.
