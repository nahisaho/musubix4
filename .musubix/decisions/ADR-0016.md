# ADR-0016: Reuse only identity-bound fresh code graphs

## Status
Accepted

## Context

The v0.1.2 `graph index`, `graph gate`, full `gate`, and change evidence paths
construct a new TypeScript Program even when the persisted code graph exactly
matches the current repository. Five repeated process-level samples measured
median durations of 3376.59 ms for `graph index` and 3138.68 ms for `graph
gate`, substantially above the other internal CLI operations. The existing
cache validates only schema version 1 and input fingerprints, so blindly
reusing it across musubix4 or TypeScript upgrades could return graph content
that differs from a complete rebuild.

## Decision

Advance the persisted graph to schema version 2 and bind it to the installed
musubix4 package version, an explicit graph-extractor algorithm version, a
package-root-relative digest of the executing extractor's complete first-party
transitive module closure, the executing TypeScript version, and exact
fingerprints for every graph input, including dependency lockfiles. Centralize
structural, producer, and canonical fingerprint validation so indexing callers
and strict consumers use the same freshness classification.

Use four explicit cache policies. `read-write` reuses an exact fresh graph and
otherwise rebuilds and atomically replaces it. `cache-read-only` reuses an exact
fresh graph and otherwise rebuilds in memory without writing. `refresh` never
reads, always rebuilds, and atomically replaces the cache. `bypass` does not
read or write the cache and always rebuilds. Preserve the existing boolean
`indexGraph` argument by mapping `true` to `read-write` and `false` to
`cache-read-only`; expose an options form for forced isolation and
per-invocation telemetry. `graph index --changed` uses `refresh`; graph impact
and cycles remain strict consumers that reject unusable caches. Existing
`writeJson` atomic replacement remains the persistence primitive.

Expose a caller-owned operation recorder and increment
`typescriptProgramBuilds` immediately before TypeScript Program construction.
Keep the existing configured full-test command unchanged: its runner supplies
a fresh nonce and excluded sidecar path to the requirement-bound Vitest test,
then augments that test's one existing report entry only when the sidecar is
current and structurally valid. No second configured performance command or
synthetic test result is introduced.

Use a separately invoked benchmark script for wall-clock evidence. Bind its
target to the approved `.musubix/benchmarks/graph-cache-target.json` digest and
pristine v0.1.2 commit, compare the candidate against fixed v0.1.2 improvement
and rolling preceding-stable non-regression references, require every process
to succeed, and persist exact command vectors, all samples, exit codes, medians,
ratios, platform identity, source-surface identity, and pin identity. Build each
reference from its `v<version>` release-tag checkout and run it against a
separate pinned target checkout. Persist the current benchmark outcome,
including threshold failures, instead of retaining an older passing artifact.
Candidate freshness uses only the graph performance source closure plus the
benchmark script, avoiding unrelated README or Skill edits while still
invalidating graph-path changes. Operation evidence proves eliminated compiler
work; controlled elapsed-time evidence proves the release target.

## Rejected alternatives

- **Trust only source fingerprints.** Rejected because extractor, package, or
  TypeScript changes can alter graph output without changing repository bytes.
- **Always rebuild for `persist: false`.** Rejected because change evidence is
  a major repeated caller and can safely read an exact cache without writing.
- **Make cache-write failures fall back silently.** Rejected because that would
  return success while required persistence failed.
- **Use module-global counters.** Rejected because parallel tests and nested
  calls would contaminate deterministic performance evidence.
- **Add a configured performance command.** Rejected because it changes the
  trusted policy baseline when the existing full-test report can carry the
  measured operation evidence safely.
- **Bind benchmark freshness to the entire publish payload.** Rejected because
  documentation or Skill-only changes would force an unrelated three-build
  benchmark and make routine quality refresh impractical.
- **Use the current working tree as the benchmark target.** Rejected because
  target drift would make before/after samples incomparable and the evidence
  non-reproducible.
- **Use elapsed time as the only performance proof.** Rejected because host
  scheduling and filesystem cache state are nondeterministic.

## Consequences

Warm graph commands avoid TypeScript Program construction and preserve exact
cached output and timestamps. Cold, stale, forced, and producer-incompatible
requests retain complete indexing. Cache schema v1 becomes intentionally
unusable after upgrade and is rebuilt by indexing commands; strict read-only
consumers continue to request an explicit `graph index`. Dependency lockfile
changes now invalidate the graph. The public boolean call shape remains source
compatible, while advanced callers can select an explicit policy and recorder.
The full-test runner gains a fail-closed nonce handshake, and release work must
regenerate benchmark evidence whenever the governed graph performance source
surface changes. Benchmark target changes require a separately approved
requirements amendment.
